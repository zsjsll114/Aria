# 空间音频与虚拟声场 — 技术方案

> 2026-10-04 · 状态：**P1 + P2 已实现**（见文末「实现记录（P1/P2）」）
> 关联：`docs/原生输出-WASAPI独占.md`、`web/src/core/equalizer.js`、`src-tauri/audio/src/dsp/`

## 0. 结论先行

Aria 有**两条并行的播放路径**，这是本方案的全部复杂度来源：

| | Web 路径（默认） | Rust 路径（WASAPI 独占开启时） |
|---|---|---|
| 触发 | 始终存在 | 设置 → 音效 → WASAPI 独占输出 打开 |
| 链路 | `audio` → `MediaElementSource` → `deckGain` → `mixBus` → `filter[0..9]` → `DynamicsCompressor` → `destination` | `ring` → `EQ(10段 biquad)` → 音量 → WASAPI |
| 实现文件 | `web/src/core/equalizer.js` | `src-tauri/audio/src/dsp/` + `engine.rs` 输出线程 |
| 现成能力 | Web Audio 全套：`ConvolverNode` / `PannerNode` / `StereoPannerNode` / `ChannelSplitter`+`Merger` | 仅 `wasapi` + `symphonia`，**卷积与 HRTF 要手写** |

`dsp/biquad.rs` 文件头已把跨路径一致性写死为硬约束：

> 若两边系数设计不同，同一组 EQ 增益会听出**不同的音色**，用户会认为"切到原生后端音质变了"——这个 bug 极难归因，因为两边各自看都"对"。

⇒ **任何新增 DSP 都必须两条路径同时落，且 A/B 盲听无差异。** 只做一条路径会出现「开独占后功能静默失效」这类最难查的问题（参考 MV 偏移检测因 `mvLayerVisible()` 判定错误而永不执行的那次）。

**分期建议（也是推荐落地顺序）**：

- **P1 · Web 侧先行**：`equalizer.js` 插节点。改动集中、可当天真机验证，**先跑通听感与 UI**。
- **P2 · Rust 侧对齐**：`dsp/` 新增模块，系数/算法与 P1 逐字对齐。需要真机 AB 对比。
- **P3 · 一致性守门**：写一条测试钉住两侧档位→参数的映射表（见 §5）。

## 1. 两个功能的定义与听感目标

用户拍板：**两个独立开关 + 档位**（关 / 轻 / 中 / 强 三档或滑杆），互不干扰。

### 1.1 空间音频（Spatial Audio）

**目标**：把「贴脸、两耳、平坦」的立体声，变成有**前方声场深度与定位感**的听感。人声居中偏前，伴奏铺开在两侧与后方，像坐在小型演出现场。

**做法**：HRTF 卷积（Head-Related Transfer Function），即用一对实测的双耳冲激响应（IR）对立体声做卷积。这是「虚拟耳机环绕」的通用做法。

- **档位即干湿比**：`dry = 1 - wet`，`wet ∈ {0, 0.35, 0.6, 0.85}`（轻/中/强）。
- 三档差异要**可闻但不夸张**：强档也不能把人声推远到"歌手跑了"。
- 关键取舍：HRTF 卷积**天然损失高频细节**（IR 是低通的），所以要补一条**直达声支路**（dry）保清晰度。纯 wet 一定糊。

**IR 素材来源（三选一，按推荐排序）**：

| 方案 | 说明 | 成本 | 风险 |
|---|---|---|---|
| A. 内置一对通用 IR | 打包 ~2 个 WAV（各 512 taps @48k ≈ 32KB），选一对中性、不过分染色的小房间/耳廓 IR | 最低 | 音染固定，不能选"厅" |
| B. 生成式 IR | 用简易头模型（球体 + 耳廓延迟）在启动时算一对 IR | 无素材 | 效果平淡，不如实测 IR |
| C. 多组 IR 可选 | 打包 3~5 对（近场/厅堂/露天），让用户选 | 素材与 UI 都变重 | 产品面变大 |

**推荐 A**：一对内置 IR + 三档干湿比。后续若要扩展再加 C。

### 1.2 虚拟声场（Virtual Soundstage）

**目标**：把声场**横向拉宽**，器乐分离度提升，像从"两个点"变成"一片"。这是**不做 3D 定位**的纯展宽，与空间音频互补（可以只开这个，人声位置不变但伴奏铺开）。

**做法（三档递进，成本递增）**：

| 档 | 算法 | 复杂度 | 听感 |
|---|---|---|---|
| 轻 | **中侧（M/S）处理**：S 通道 ×1.3，M 不动 | 极低（增益一次） | 轻微展宽，副作用最小 |
| 中 | **Haas 延迟**：左声道延迟 ~10~20ms 混入右耳（微延时展宽） | 低（DelayNode） | 明显变宽，有包围感 |
| 强 | **跨耳抵消（Crosstalk Cancellation）**：左右扬声器串音在耳道被抵消，模拟耳机式包围 | 高（需一对短 FIR 或 lattice 滤波器） | 包围感最强，**对相位/延时极度敏感，易出梳状滤波** |

> **★★ 实现必须按 M/S 形式，别写成"同相串音"**（P1 踩过这个坑，见实现记录）：
> 「把 L 串一点到 R、R 串一点到 L」是**同相串音（crossfeed）**，效果是**收窄**：
> `S_out = S_in·(1−k)`（k>0）。耳机的 Bauer crossfeed 就是靠它**减少**宽度。
> 真展宽（`S_out = S·S_in`, S>1）对偶地要求**反相注入对侧**，同时把同侧同步抬高：
> `a = (1+S)/2`（同侧）、`b = (1−S)/2`（对侧），`out_L = aL + bR`、`out_R = bL + aR`。
> 关键性质 **`a + b ≡ 1` ⇒ 单声道和 (L+R) 精确不变**（不抵消）——这才是「几乎零风险」的来源。
> 只把一侧反相而不抬同侧（`1+|b|` 削弱 L+R）才是会翻车的写法，本方案不采用。

**推荐做法**：轻档用 M/S（几乎零风险），中档叠 Haas，**强档先不上跨耳抵消**——先把 轻/中 两档做实，强档留作 P2 再评估（跨耳抵消在扬声器上效果远好于耳机，而 Aria 用户多半戴耳机，收益可能不值得复杂度）。

**⚠️ 单声道兼容性**：M/S 展宽与 Haas 都会**改变单声道下的相位**。必须验证「左右相加后」不出现明显抵消（乐器消失/中空）。这是虚拟声场最容易翻车的地方。

## 2. 信号链插入点

### 2.1 Web 侧（`web/src/core/equalizer.js` `initEqAudioGraph()`）

现有建图：

```js
state.audioCtx = new AC();
state.eqSourceNode = state.audioCtx.createMediaElementSource(_audio);
state.eqDeckGain = state.audioCtx.createGain();
state.eqMixBus = state.audioCtx.createGain();
state.eqSourceNode.connect(state.eqDeckGain);
state.eqDeckGain.connect(state.eqMixBus);
// filters[0..9] 串联
let node = state.eqMixBus;
for (const f of state.eqFilterNodes) { node.connect(f); node = f; }
window.playerLoudnessComp = state.audioCtx.createDynamicsCompressor();
node.connect(window.playerLoudnessComp); node = window.playerLoudnessComp;
node.connect(state.audioCtx.destination);
window.playerAudioAnalyser = state.audioCtx.createAnalyser();
node.connect(window.playerAudioAnalyser);
```

**插入点在 `filters[9]` 之后、`compressor` 之前**，理由：

1. 必须**在 EQ 之后** —— 用户调 EQ 的意图是"先把频谱修好"，空间处理应该在干净信号上做；反过来会让 EQ 的 shelf 影响 HRTF 的频响。
2. 必须**在 compressor 之前** —— 响度归一化要能吃到空间处理带来的电平变化；若放在 compressor 之后，`volumeNorm` 就管不住展宽后的峰值（展宽常让峰值上升 1~3dB，容易削波）。
3. 必须**在 `mixBus` 之后** —— Automix 双 deck 各自 `source→gain→mixBus`，挂在 mixBus 后只需**一套**空间节点；挂前面会每条 deck 一套（4 倍节点，且两条 deck 的展宽互不相干，交叉淡入时声场会跳）。

新增节点（示意，非最终代码）：

```js
// 空间音频支路（可选，wet/dry 并联）
if (spatialOn) {
    state.spatialConvL = ctx.createConvolver(); // 左耳 IR
    state.spatialConvR = ctx.createConvolver(); // 右耳 IR
    state.spatialWet  = ctx.createGain();       // wet
    state.spatialDry  = ctx.createGain();       // 1 - wet
    // splitter → convL/convR → merger  （或直接双 conv + merge）
    // node → [dry→] merge ；node → [splitter→conv] → merge
}
// 虚拟声场支路（可选，串在空间之后）
if (stageOn) {
    state.stageSplit = ctx.createChannelSplitter(2);
    state.stageMerger = ctx.createChannelMerger(2);
    state.stageSDelay = ctx.createDelay(0.05); // Haas
    state.stageSGain = ctx.createGain();       // S 通道增益
}
```

**关键约束**：

- `ConvolverNode` 的 `normalize` 默认 `true`（按 IR 能量归一化）—— **保持默认**，否则换 IR 会变响度。若必须关掉，则自己要补增益补偿。
- 节点必须支持**运行时开关**：不要 `disconnect()` 整条链再重连（会有咔哒声 + 断音），而应保持图结构常驻、只把 `wet` 增益设 0 / `dry` 设 1。**首次建图时就把节点建好**，开关只改增益。
- 参数变化用 `setTargetAtTime`（平滑 ~0.05s），**不要直接赋 `value`** —— 档位切换时直接赋值会有 zipper noise（这是 Web Audio 常见坑，`Aria.__audioOutputReapply()` 那条链路也要重新走一遍）。
- 新增节点后 `Aria.__audioOutputReapply()` 逻辑不变（该钩子只关心 `MediaElementSource` → sink 的目标切换）。

### 2.2 Rust 侧（`src-tauri/audio/src/dsp/`）

现有链（`dsp/mod.rs` 声明）：

```
ring ──► EQ（10 段 biquad）──► 音量 ──► WASAPI
```

**插入点在 `eq.process_interleaved()` 之后、音量乘之前**，与 Web 侧语义对齐（在 EQ 后、响度前）。

新增文件 `dsp/spatial.rs`（与 `eq.rs` 并列），并在 `mod.rs` 的链序注释里登记：

```rust
pub struct SpatialChain {
    // HRTF 双耳 FIR（每耳一条），用 double-buffered 系数
    fir_l: FirFilter,
    fir_r: FirFilter,
    wet: f32,
    // 虚拟声场
    stage: StageState,   // M/S + Haas delay line
}
impl SpatialChain {
    pub fn process_interleaved(&mut self, buf: &mut [f32]); // in-place 立体声交错
    pub fn apply(&mut self, s: &SpatialSettings);
}
```

**Rust 侧与 Web 侧的三个差异点**（必须在实现时特别注意）：

1. **没有现成 ConvolverNode**：Web Audio 的 `ConvolverNode` 用 **FFT 分块卷积**（partitioned convolution），对 512~2048 taps 的 IR 开销可忽略。Rust 侧若直接写时域 FIR（512 次乘加/样本/耳），48kHz 立体声 = 512 × 48000 × 2 ≈ **4900 万次乘加/秒**，单核能吃下但明显。**建议**：IR 不超过 **256 taps**，或上 FFT 分块卷积（需引入 `rustfft`）。**先测再用**。
2. **Haas 延迟** = 一条环形延迟线，`ring.rs` 的 `VecDeque` 结构可复用思路，但这是**固定小缓冲（<50ms）**，直接开 `[f32; N]` 环形数组更省。
3. **采样率不固定**：Rust 侧保留源采样率（bit-perfect 直通），所以 IR 与延迟时间都要**按 `output.sample_rate()` 重采样/换算**。Web 侧的 `AudioContext` 采样率通常 48k 固定，但也可能是 44.1k —— **两边都不能假定 48k**。这是最容易两边不一致的地方。

### 2.3 WASAPI 独占下的行为

独占开启时：
- Web Audio 图**整条不生效**（引擎由 Rust 接管），所以 Web 侧的空间节点形同虚设。
- ⇒ **必须**由 Rust 侧承担该功能，否则用户一开独占就"听不到空间音频"，且他不会知道为什么。
- **反面**：如果 Rust 侧暂未实现（P1 阶段），则应**在 UI 上把开关置灰并说明「WASAPI 独占输出下暂不可用」**，而不是静默无效。这是 P1 必须带的降级提示。

## 4. 与既有功能的交互

| 交互对象 | 处理 |
|---|---|
| **EQ** | 串在 EQ 之后（§2.1）。`applyEqGains` 不受影响。 |
| **响度归一化 `volumeNorm`** | 空间处理必须在 compressor 之前（§2.1 理由 2）。若展宽导致削波，靠 compressor 兜。**但要实测**：compressor 的 `threshold -22 / ratio 3.2` 是为"人声为主"调的，展宽后峰值分布变了，可能需要微调。 |
| **Automix 交叉混音** | 挂在 `mixBus` 后 ⇒ 交叉淡入期间两首歌共享同一套空间节点。**风险**：两首歌同时经过 HRTF 卷积，wet 叠加可能过载。建议交叉期 wet 不变（不做动态调节，先观察）。 |
| **WASAPI 独占** | ~~P1 阶段该功能不可用 → **UI 显式置灰 + 提示**（§2.3）。~~ **P2 已补 Rust 侧 ⇒ 置灰解除**（实现记录 §P2）。 |
| **变速（playbackRate）** | 变速会改采样率感知吗？Web Audio 里 `playbackRate` 在 source 层，空间节点在后 ⇒ **不受影响**。Rust 侧同理。 |
| **极端性能模式** | 建议**跳过**空间处理（HRTF 卷积是最贵的音频 DSP）。参考 MV 同步的既有做法：极端性能模式跳过。 |
| **本地文件歌曲 / 在线流** | 无差异，空间处理在解码后、输出前，与源无关。 |
| **设置 → 外观的预览播放器** | 预览播放器声音走同一 `audio` 元素吗？需确认；若是独立元素，可能需要单独接线或直接不接（预览不需要空间效果）。 |

## 5. 一致性守门（P3）

`biquad.rs` 的教训：**两边参数必须同一张表**。做法：

**唯一参数源**：定义档位 → 参数的映射表，两侧**逐字照抄**（不共享代码，共享数值与注释）：

```js
// Web: web/src/core/spatialTuning.js
export const SPATIAL_TUNING = {
    light:  { wet: 0.35, stageS: 1.10, haasMs: 0  },
    medium: { wet: 0.60, stageS: 1.25, haasMs: 8  },
    strong: { wet: 0.85, stageS: 1.45, haasMs: 16 },
};
```

```rust
// Rust: src-tauri/audio/src/dsp/spatial_tuning.rs（数值与上面完全一致）
pub const SPATIAL_TUNING: [SpatialTuning; 3] = [ /* 同上 */ ];
```

**测试**（`tests/js/test_spatial_tuning.js`）：断言两边的表数值逐项相等（读 Rust 源文件正则提取对比，或生成 JSON 供两边消费 —— 后者更可靠）。

> 推荐**生成式**：写 `scripts/build_spatial_tuning.mjs`，从一份 `spatial_tuning.json` 生成 JS 常量与 Rust 常量。这样物理上不可能不一致（同 `scripts/anime4k/` 生成 shader 的既有模式）。

**音质 A/B 验证**（真机，用户手动）：
1. 同一首歌，Web 后端 vs 原生后端，同一档位，切输出后端听。
2. 判据：**切换时应只有"定位/宽度"一致，没有"变亮/变暗/变响"**。若音色变了 → 系数不等价。

## 6. 性能预算

| 项 | Web 侧 | Rust 侧 |
|---|---|---|
| HRTF 卷积 512 taps | `ConvolverNode` FFT 分块，~0 | 时域 4900 万 MAC/s（偏高，建议 ≤256 taps 或上 FFT） |
| M/S 展宽 | 每样本几次乘加，~0 | 同 |
| Haas 延迟 | `DelayNode`，~0 | 环形数组读，~0 |
| 内存 | 节点对象 + IR buffer（~32KB×2） | IR ~32KB×2 + 延迟线 |

**结论**：Web 侧性能无忧（`ConvolverNode` 是原生实现）。**Rust 侧是风险点**，必须先用 `audio-probe`（参考 `docs/原生输出-WASAPI独占.md` 的探针）量化，再决定 IR 长度与是否引入 `rustfft`。

⚠️ 注意用户笔记本 dGPU 会被 EC 限频那条既有教训 —— 但那是 GPU，本功能是纯 CPU DSP，不受影响。**但要注意与 MV 画质增强（WebGL 上行渲染）抢 CPU**：两者同时开时，若出现爆音/卡顿，优先怀疑 CPU 争抢。

### ★★ P1 的真 bug：虚拟声场方向写反了（本次修正）

P1 的 Web 拓扑是 `out_L = L + k·R`（同相串音，k>0），数学上
`S_out = (L−R)/2 · (1−k)` ⇒ **S 被缩小 = 收窄**，与「虚拟声场」的名字与目标相反。
（耳机上的 Bauer crossfeed 正是这个原理，用来**减少**宽度。）
P1 注释里「向对侧注入同相信号会增大 S 分量」是**方向写反**。

**修正**（两侧同时改）：M/S 形式 `a=(1+S)/2` 同侧、`b=(1−S)/2` 对侧（S>1 时 b<0 = 反相），
`out_L = a·L + b·R`、`out_R = b·L + a·R`。`a+b ≡ 1` ⇒ **单声道和精确不变**、S ×S 真展宽。
不再做峰值补偿（a ≤ 1.16，最大抬升 ≤ +1.4dB），为的是保住 `a+b≡1` 这条不变量。
回归测试 `virtual_stage_widens_and_preserves_mono_sum` 同时钉住「差变大」与「和不变」。

> 教训：P1 的探针只验证了「增益被正确写入节点」，**没验证效果方向**。参数铺对了 ≠ 功能做对了。

### 空间音频（P2 新增，两路径同时落）

- **IR 是生成式的**（方案 §1.1 备选路线）：无实测 HRTF 素材（体积 + 授权），
  故按「简化头模型 + 早期反射场」在构建期合成 3 组（近场/厅堂/宽阔），
  样本**逐字写进两侧源码**（不是两边各写一份合成代码——那会分叉）。
- **是「短 IR」**：512 taps @48k ≈ 10.7ms，只含头相关早期反射，**不含长房间混响尾**。
  被 Rust 时域 FIR 成本卡死（§2.2/§6：>512 taps 需 `rustfft`）。与 §1.1「小房间/耳廓 IR」一致。
- **归一化前置**：生成期按能量归一（两耳共用同一因子），Web 侧把 `ConvolverNode.normalize`
  显式设 **false**——绕开「浏览器归一化口径」这第三个变量（§2.1 允许，条件正是自补增益）。
- **重采样**：IR 固定 48k，输出可能是 44.1k/96k/192k（独占保留源采样率）；
  两侧用**同一个**线性插值函数（生成器同时产出 JS 与 Rust 版）。
- **dry/wet 并联**：`out = dry·(1−w) + wet·w`，w 即档位（0.35/0.60/0.85）。

### 实测：空间链 CPU 成本（`audio-probe spatialbench`，20s 音频，两开关都开）

| 采样率 | taps（重采样后） | 单核占用 |
|---|---|---|
| 44.1k | 470 | 1.96% |
| 48k | 512 | 2.49% |
| 96k | 1024 | 8.77% |
| 192k | 2048 | **40.3%** |

★ 成本 ∝ taps × 采样率，而 taps 随采样率线性增长 ⇒ **总成本 ∝ 采样率²**（48k→192k = 16×）。
★ 实测 `opt-level="s"`（发布版档位）与 `opt-level=3` 差异 **<5%**（FIR 内层循环太简单）。
★ 结论：常见档（44.1/48k）**~2.5% 单核，可忽略**；192k 是高成本但**仍实时可跑**（余量 60%）。
若将来 192k 场景变得重要，两条可选路：① 对 FIR 长度设上限（牺牲高采样率下的 IR 时长）；
② 引入 `rustfft` 做 FFT 分块卷积。**目前不做**——先按方案 §5 让用户做真机 A/B 盲听再定。

### 顺手修掉的两个真 bug（都是「量化/测试发现」而非「看代码发现」）

1. **f32 平滑停滞**：单极平滑在增益逼近 1.0 时，每步减量降到 `f32::EPSILON` 的半个 ULP
   以下而被舍回原值 ⇒ **永久停滞在 `ULP(1.0)/(2k) ≈ 1.43e-4`**（`a` 死咬 1.000143），
   既够不着吸附阈值，又留下 ~1.07e-4 的透明性残差。
   **修**：平滑累加改 f64（停滞点降到 ~2.6e-13）。单测 `turning_off_is_transparent_after_settling` 钉住。
2. **非 48k 越界 panic**：`taps` 曾用常量 `IR_TAPS`（512）做 FIR 循环上界与历史缓冲长度，
   而 44.1k 下 IR 重采样后是 **470** ⇒ `index out of bounds: len is 470 but index is 470`。
   所有单测只跑 48k（那时两者恰好相等）**集体漏过**，是 `spatialbench` 扫 44.1k 时炸出来的。
   **修**：`taps = fir_l.len()`（重采样后的实际长度）+ 回归测试 `works_at_every_sample_rate_with_spatial_on`。
