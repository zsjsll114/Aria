# 歌手页面技术方案（设计文档）

> **落地状态（2026-10-03）**：Phase 1 已实现并通过真机验证。
> 第一～八节保留当初的设计原貌；**实测与原设计的偏差、真实改动清单、遗留项见文末第九节**——
> 其中若干条是文档推断与实测不符的地方，以第九节为准。
>
> 适用对象：Aria（网页版 + Tauri 桌面壳）。
> 前置基础：应用内全部二级页面均为「全屏 overlay + `.visible`」形态
> （搜索 / 收藏 / 歌单 / 榜单 / 最近 / 统计 / 自建收藏），无前端路由。
> 本文描述在其上新增「歌手页」的设计，**不含实现代码**。

## 一、现状核查（先给结论）

| 结论 | 证据 |
|---|---|
| 项目里**没有任何**歌手页、歌手入口 | `grep -rn "artistOverlay\|singerOverlay\|artistPage\|歌手页" web/src web/index.html` → **0 命中** |

**一句话**：能力（上游接口）已经就位，缺的是 ①ID 采集 ②入口 ③页面。

## 二、目标与范围

### 做

1. 搜索 / 榜单 / 歌单 / 收藏 / 最近列表里的**歌手名可点击**。
2. 点击进入 **overlay 歌手页**：头像、名称、粉丝数、简介（可折叠）、热门歌曲、专辑、相似歌手。
3. 歌手页里的歌曲可直接播放 / 加入队列 / 收藏 / 加歌单——复用现有动作函数，不新增播放链路。
4. 音源标识贯穿始终：页面顶部显示歌手来自哪个平台，歌曲列表沿用现有 `Aria.__platformIconHTML` 平台角标。

### 不做（本方案明确排除）

- 不做前端路由 / URL 深链（全项目无先例，Tauri 窗口 URL 固定 localhost，加路由会牵动 `src-tauri/src/lib.rs`）。
- 不做歌手关注 / 收藏歌手（汽水有 `collectArtist`，其余三源需登录态，收益低）。
- 不做跨源"同一歌手合并"（ID 域不通，见第六节风险 1）。
- 不做独立的歌手列表浏览页（Phase 3 再说）。

## 三、数据源能力清单

全部走 `/api/selfhost/{src}/proxy?path=<URL-encoded>`（4s 超时、失败静默回退）。

### QQ音乐（`tencent` · qq-music-api-node）

| 用途 | 路径 | 参数 |
|---|---|---|
| 简介 | `/getSingerDesc` | `singermid` |
| 热门歌曲 | `/getSingerHotsong` | `singermid`, `limit`(**默认 5，必须显式传 50**), `page` |
| 专辑 | `/getSingerAlbum` | `singermid`, `limit`(默认 5→传 30), `page` |
| 粉丝数 | `/getSingerStarNum` | `singermid` |
| 相似歌手 | `/getSimilarSinger` | `singermid` |
| 分类筛选 | `/getSingerCategory` | — |
| 分类列表 | `/getSingerList` | `area`, `sex`, `genre`, `index`, `page` |

（路径与参数取自 `_eval/qq-music-api-node/src/routes/api-metadata.ts:558-640`）

### 网易云（`netease` · NeteaseCloudMusicApi）

| 用途 | 路径 | 参数 |
|---|---|---|
| **详情 + 热门 50 一步到位** | `/artists` | `id` |
| 全部歌曲（可翻页） | `/artist_songs` | `id`, `limit`, `offset`, `order` |
| 专辑 | `/artist_album` | `id`, `limit`, `offset` |
| 简介 | `/artist_desc` | `id` |
| 相似歌手 | `/simi_artist` | `id` |
| 分类列表 | `/artist_list` | `area`, `type` |

> `/artists` 一次返回 `{artist:{...}, hotSongs:[...]}`，是四源里最省事的一个——MVP 首选。

### 酷狗（`kugou` · KuGouMusicApi）

| 用途 | 路径 | 参数 |
|---|---|---|
| 歌手详情 | `/artist_detail` | `id`（内部映射 `author_id`，POST，`module/artist_detail.js:3-11`） |
| 单曲 | `/artist_audios` | `id`, `pagesize`, `page`, `sort`(`hot`/`new`，`:9-10`) |
| 专辑 | `/artist_albums` | `id` |
| 歌手列表 | `/singer_list` | `type`, `sextype`, `hotsize`（`module/singer_list.js:2-17`） |

### 汽水（`qishui` · ly-music-source）

vendor 有 `getArtist(artistId)` / `listArtistTracks(artistId, opts)` / `listArtistAlbums(artistId, opts)`，
但 **`scripts/qishui-server.mjs` 未暴露**。要支持需在适配层补三条路由（`/artist`、`/artist/tracks`、`/artist/albums`），
与现有 `/search` 同款写法（`qishui-server.mjs:316`）。**列为 Phase 3。**

### 酷我（`kuwo`）

**没有** vendor 服务（`_eval/` 只有四家），无歌手接口 → 酷我来源的歌手名不做可点（或降级为跨源搜索，见第六节风险 1）。

### 4.2 数据契约（四源归一化后）

```js
// 歌手摘要（列表/入口用）
{ source: 'tencent'|'netease'|'kugou'|'qishui',
  artistId: string,     // QQ=singerMid, 网易=id, 酷狗=author_id, 汽水=artistId
  artistMid: string,    // QQ 专用；其余为空
  name: string }

// 歌手详情（页面用）
{ source, artistId, name, avatar, fans, desc,
  songs: [{ song, singer, album, cover, interval, source, id, mid }],  // 复用搜索页字段形状
  albums: [{ name, cover, year, id }],
  similar: [{ source, artistId, name, avatar }] }
```

**关键原则：新增字段，不改旧字段。** 归一化时保留 `singer` 字符串原样不动，另加 `artists: [{id, mid, name}]`。
这样现有 10 个渲染点零改动、零回归，只有要做入口的地方才读新字段。

## 六、风险与坑（按优先级）

1. **跨源 ID 不通（必须接受的设计约束）**
   QQ 的 `singermid`、网易的 `id`、酷狗的 `author_id`、汽水的 `artistId` 互不相干，没有映射表。
   策略：**在哪一源看到歌手，就用哪一源打开**（数据里带 `source`）。真的没有 ID 时（本地音乐、酷我、老收藏）把入口降级为「以歌手名发起搜索」，并给用户一句明确提示，**不要静默失效**。

2. **酷我无歌手接口** → 酷我来源不做可点入口。

3. **头像协议** → 网易 `picUrl` 是 `http://pX.music.126.net`，必须升 https（现成先例 `150-search-engine.js:123-127`），否则 WebView2 mixed-content 拦图 → 头像永久空白。

4. **QQ 简介带 HTML** → `/getSingerDesc` 返回的简介常含标签与转义实体，落 DOM 前先剥标签、再 `esc()`。**不能直接插 innerHTML。**

5. **`limit` 默认值陷阱** → QQ `/getSingerHotsong` 的 `limit` 默认只有 **5**、`/getSingerAlbum` 默认 **5**。不显式传就是"热门歌曲只有 5 首"的假象，极易被误判为接口缺数据。

6. **汽水适配层改动面** → 需要动 `scripts/qishui-server.mjs`（受版本控制，可改），但 `_eval/` 不入库；改完要按 `AGENTS.md` 的方式验证（`python -m unittest tests.python.test_vendor_loopback_guard` 仍绿）。

7. **点歌手名会开始放歌（最容易漏的交互 bug）**
   搜索结果整行是播放热区（`150-search-engine.js:487-491`）。`.artist-link` 的 handler 不 `stopPropagation()` 的话，点歌手名的副作用是**开始播放这首歌**——这是最容易在自测时被忽略、上线后被用户骂的那类 bug。

8. **桌面版同步**（工作记忆记录过的坑）
   改完 `web/` 必须 `robocopy` 同步到 `dist/AriaPortable/web/`（src + vendor + 根 html），否则用户跑桌面版永远看不到新页面。`server.py` 若改动才需重打包 `server.exe`（本方案不涉及）。

9. **不做持久化缓存** → 歌手信息时效性弱、体积不可控；只用内存 `Map`，键 `source:artistId`，上限 100 条 LRU 即可。避免污染 `cache/`。

### 9.2 实测与原设计的偏差（以本节为准）

| 原设计写法 | 实测结论 |
|---|---|
| QQ 可用 `remoteplace=singer` 搜歌手 | ❌ **无效** —— 传 `singer`/`txt.yqq.singer` 都返回 `singer: null`，仍是歌曲结果。QQ 侧只做「歌曲里顺带带出歌手对象」；关键词搜歌手**只有网易、酷狗**支持 |
| 酷狗歌手接口是 `/artist_detail` | ❌ 实际路由是 **`/artist/detail`**（函数名 `artist_detail`，路由带斜杠）；且 `artist_detail` 内部是 **POST**，GET 直接 404 |
| 网易专辑接口是 `/artist_album` | ❌ 实际是 **`/artist/album`**；`/artist_album` 会返回 **空** `hotAlbums`（不报错，静默空——最容易被误当成"该歌手没专辑"） |
| QQ 简介「带 HTML 标签，需剥标签」 | ❌ 实际是 **XML 字符串**：`{response: "<?xml …<desc><![CDATA[简介]]></desc>"}`，需从 CDATA 里抠（`qqDescFromXml()`） |
| 「QQ `/getSingerHotsong` limit 默认 5」 | ✔ 属实，已显式传 50 |
| （设计未覆盖） | 🔴 **新发现真 bug**：前端拼 `/api/selfhost/${source}/proxy` 用的是搜索页签的 `tencent`，而后端 `_SERVICES` 的键是 `qq` → 恒 404，被 `catch { return null }` 静默吞掉。**QQ 自建 vendor 的搜索与歌词从未真正生效过**，一直悄悄回退公网 vkeys —— 这正是 AGENTS.md 里「QQ 单页从 100 缩水到 60」的真实原因。已用 `selfhostKeyOf()` 收口 |
| （设计未覆盖） | QQ `/getSingerStarNum` **404**（路由在 metadata 里但不可用）→ QQ 侧不显示粉丝数 |
